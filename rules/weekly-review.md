# 每周审阅机制

## 1. 目标

用一次低成本、可重复的审阅，回答六个问题：
1. 环境是否健康、权限是否过大、依赖是否可用？
2. 哪些组件重复、过时、闲置、高风险，应该合并/替换/清理？
3. 是否有值得升级的版本/模型/工具？收益和风险是什么？
4. 任务成功率、质量、Token、费用、耗时如何？失败根因是什么？
5. Agent 分工、工具组合、知识共享、自动化流程哪里可以改进？
6. 本周做了什么改进、实际收益、遗留风险、下周做什么？

## 2. 执行方式

**首选 Agent 原生自动化**：
- DSH：`schedule_create` 建周任务（每周日 20:00），提醒内容为“运行 evolution 周审阅与自主维护”。
- Codex：`~/.codex/automations/` 或平台 automations。
- Claude Code：平台 scheduled tasks / routines。
- 其他：优先查平台自带 scheduler，不先装外部计划任务。

```bash
# 生成原生自动化提示（DSH/Codex/Claude 通用文本）
python ~/.agents/skills/evolution/scripts/evolution.py schedule native

# 手动（所有平台）
python ~/.agents/skills/evolution/scripts/evolution.py review

# 指定周与联网检查（默认离线）
python .../evolution.py review --week 2026-W45 --online

# 仅当平台没有原生调度时，才回退到 OS 计划任务/cron
python .../evolution.py schedule install --driver os --apply
python .../evolution.py schedule status
python .../evolution.py schedule remove --driver os --apply
```

**固定顺序（v1.3.0 起，环境优先）**：
1. `envcheck --online`：先确认环境本身没有拖后腿。plugin_compat 为 FAIL 时必须本周处理（升级或卸载），不许只豁免。
2. `evolve --apply --bump patch --release`：指标/审计/环境/维护 → 学习假设 → 低风险规则 → 测试 → 版本升级；无新学习项不升版本。
3. `review --apply --online`：去重、隔离无效技能、检查升级候选、审计、周报。
4. `plugins --apply --online`：只升级同 major；跨 major 只报告；升级后必须提示重启 DSH。
5. `cleanup --apply`：清理缓存与过期产物（备份默认保留）。

顺序不能倒：环境有硬伤时，指标与审计的结论都在打折。
- `--evaluate` 用后续指标判断实验 keep/regress；regress 记录并复核，不静默保留。

**周任务边界（2026-11-07 用户授权自主维护）**：
- 自动执行：同内容技能去重（改为 junction）、无效技能隔离、同 major 插件/技能升级、`install_queue` 按需下载。
- 每个删除/替换先 `snapshot` 并单独备份；失败恢复；记录到 `state/maintenance-latest.json`。
- 停止条件：跨 major、付费、外发敏感数据、未备份删除、删除用户手写技能；这些只报告不执行。

不支持任何自动化的平台：把 `review` 加入项目日历/README 提醒；或由 CI 每周运行并上传报告。

## 3. 审阅清单

### A0. 环境年代感（先做）

- [ ] `envcheck` 是否有 FAIL 项？plugin_compat / plugin_tree 优先
- [ ] 模型通道 provider/model/reasoningEffort 是否显式且合理
- [ ] 锁文件是否落后于依赖清单
- [ ] 运行时是否 EOL 或临近 EOL
- [ ] 本地技能是否覆盖了插件内置技能（可能压住修复版本）
- [ ] 上一份周报距今多久（>28 天即为 high）

### A. 环境审计
- [ ] Python/Node/Git 等运行时版本与路径
- [ ] 技能根、运行时目录、报告目录可写
- [ ] Skill 数量、无效 frontmatter、断链、重复名
- [ ] MCP 服务：命令/URL、环境变量名（不读值）、是否固定版本
- [ ] 插件/依赖：版本、来源、许可证、是否归档/停维护
- [ ] 权限预设：是否长期 danger-full-access / approval never
- [ ] 调度任务是否存在、上次运行结果、日志
- [ ] 磁盘/日志/快照占用

### B. 断舍离
- [ ] 同名/同内容技能：保留权威源，其余链接或归档
- [ ] 近 180 天未修改且无使用记录：标记“待观察”，不直接删
- [ ] 重复 MCP/插件：合并或禁用，保留一个权威入口
- [ ] 过时/停维护依赖：列替代方案，验证后替换
- [ ] 高风险组件：权限过大、未固定版本、明文 HTTP、混淆脚本
- [ ] 自有产物清理：旧报告（>180 天）、旧快照（>90 天）、失败导出包；先 dry-run

### C. 更新升级
- [ ] 只检查配置中 `upgrade_watch` 的仓库/包，避免全网漫游
- [ ] 记录当前版本、最新版本、发布日期、破坏性变更
- [ ] 收益验证：性能/稳定性/安全/能力，至少一项有证据
- [ ] 风险：许可证、依赖、配置迁移、回滚成本
- [ ] 结论：observe / trial / upgrade / reject；默认 observe
- [ ] 同 major 可自动升级；跨 major 只报告
- [ ] 升级前 snapshot；升级后 doctor + 回归；失败 rollback

### D. 性能
- [ ] 任务数、成功率、部分成功、失败
- [ ] p50/p95 耗时、Token、费用
- [ ] 人工干预次数、重试次数、工具调用数
- [ ] 失败分类：信息不足、工具故障、权限、方案错误、验证不足、外部依赖
- [ ] 资源浪费：重复读取、重复搜索、无效并行、过长上下文

### E. 架构
- [ ] 是否有职责重叠的 Agent/技能
- [ ] 是否有可以固化为脚本/命令的重复流程
- [ ] 知识是否集中、可检索、无重复
- [ ] 自动化是否覆盖高频、低风险、可验证的环节
- [ ] 是否引入了不必要的常驻服务/权限

### F. 报告
- [ ] 结论先行，问题按 P0/P1/P2 排序
- [ ] 每项改进有证据（命令、数字、文件路径）
- [ ] 明确“未检查项”和限制
- [ ] 下周 1-3 个可执行动作
- [ ] 报告写入 `reports/weekly/` 并更新索引

## 4. 指标口径

| 指标 | 口径 |
|---|---|
| 成功率 | success / 总任务；partial 单独统计 |
| p50/p95 | 任务耗时或 Token 的分位数（样本 ≥5 才报告） |
| 人工干预率 | interventions > 0 的任务占比 |
| 重试率 | retries > 0 的任务占比 |
| 单位产出成本 | 总费用 / 成功任务数；无费用数据则不计算 |
| 失败根因 | 使用固定枚举，便于趋势比较 |
| 数据可信度 | 样本量、采集方式、缺失字段；不足时明确“数据不足” |

**禁止**用估算值冒充实测值；没有数据就写“无数据/样本不足”。

## 4.5 环境年代感口径

| 指标 | 口径 |
|---|---|
| 环境分 | 100 - Σ(严重度权重)，权重见 `references/envcheck.md` |
| 兼容性失败数 | 宿主自述启动拒绝的插件条数；非 0 即为硬伤 |
| 心跳天数 | 最近周报 mtime 距今天数 |
| 可自动修复项 | finding 中 `auto_fixable=true` 的条数 |

报告必须区分"已修复"与"仅报告"；分数下降但没有新增发现时，说明是另一项变差，要指出是哪项。

## 5. 报告模板

```markdown
# 每周进化审阅 · 2026-W45

## 结论
- 健康度：绿/黄/红（依据）
- 本周最重要的 3 个发现
- 已执行的改进（含验证）
- 需要用户决策的事项

## 环境
（表格：组件、状态、证据）

## 断舍离
（候选、影响、建议、是否执行）

## 升级
（当前→候选、收益、风险、结论）

## 性能
（指标表 + 失败根因 + 浪费点）

## 架构
（改进点、预期收益、成本）

## 风险与未检查项
（明确边界）

## 下周动作
1. ...
2. ...
```

## 6. 节奏与保留

- 每周一次；繁忙时可改为双周，但不得无限期跳过。
- 报告保留 180 天；JSON 保留 365 天；快照保留 90 天。
- 连续两周无数据/无变化时，报告应缩短，避免形式主义。
- 审阅本身也要控制成本：默认离线、只扫配置的根、限制文件大小与数量。
